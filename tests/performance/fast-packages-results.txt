Compatibility fix
An accelerated content hash can compile a WASM kernel on first use. Nodepod's
patched Module constructor was trying to hash that kernel for the WASM cache,
recursively initializing the hash. The cache now bypasses lookup/registration
while a synchronous content hash is in progress, then resumes normal caching.
The guard is generic and names no package. A cold-bootstrap regression checks
that compilation terminates, the digest matches Node crypto, and subsequent
module lookups work. No guest framework code or browser timer API is patched.

Native runtime comparison
Node v24.16.0, Windows. Same-process bundles against each checkout's own
dependencies; seven rounds per task, alternating AB/BA, ten warm-up calls.
Medians below are milliseconds per operation. Every task's full output checksum
matched before timing (AST, transformed text, compressed bytes, digests or

Fresh-install phase investigation (follow-up)
The original three-pair online +11% result did not reproduce. Do not treat it
as an established install regression. We cannot reconstruct its precise cause
because that original run did not capture request/installer phase timings.

Both built versions were copied to unique benchmark directories and given the
same lightweight span collector at shell-installer construction. Checkout dist
and runtime source were not modified. SDK profiling captures process startup;
worker spans capture resolution and materialization. Span logs emit once at
install completion. Each run uses a fresh browser context and empty IDB, so
first-use WASM initialization is included, although not separately isolated.
One warm-up per version was excluded, followed by four alternating measured
pairs in each mode. No other build/test workload ran during measurements.

Latest retained-run medians (ms):
phase                       live old   live new   replay old   replay new
process spawn               178.28     161.83     184.33       176.75
dependency resolution       502.38     502.44     476.10       485.49
package materialization     599.94     485.30     567.43       497.20
whole fresh npm install     1318.90    1176.73    1268.27      1184.41

Live: updated version 10.8% faster. Replay: updated version 6.6% faster.
Replay records all 76 registry manifests and 77 tarballs from the first warm-up
and fulfills subsequent requests with identical bodies/status/headers. Unknown
registry URLs fail rather than falling back to the live network. Browser request
timings confirm fulfilled requests have no DNS/connect/requestStart timings.
The pako CDN module and local bundle loading are still measured separately and
not replayed; this is a controlled registry comparison, not a CPU-only benchmark.

Earlier independent phase repeats also favored the update: live medians
1303.73 -> 1192.72 and 1275.34 -> 1214.40; first replay 1269.69 -> 1190.73.
Request durations varied substantially in live runs. This supports network/run
variation as a plausible contributor to the original discrepancy; it does not
prove which requests caused the original slowdown. No consistent first-use or
process-startup regression was found. Materialization is faster in every repeat.
Individual download/extraction spans overlap: their summed times must not be
added to wall time. Phase medians also need not sum to the median whole install.

Both retained profiling tests passed (20 successful installs, including warm-ups).

Validation
Full unit suite: 1,645 passed, 5 skipped. Type check and library/declaration
build passed. Five performance browser checks and seven runtime-reliability
checks passed. The comparison itself passed all eight baseline/candidate runs.
Fresh hash bootstrapping, zlib/crypto, parsing, packing/eviction, worker binary
sync, Vite/Tailwind builds, HMR state preservation, fetch bodies, process kill,
preview downloads and host-route isolation are covered.
Fast pako/hashes/lexer use WebAssembly; validate the supported browser/SIMD
matrix when adopting this beyond the tested Node/Chromium environments.
